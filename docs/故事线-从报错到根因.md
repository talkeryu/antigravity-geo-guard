# 从「被封号」到「IP 被判成中国」——一次完整的排障复盘

> 记录时间：2026-11-21 ~ 11-22
> 环境：macOS 27.2 (arm64)、Antigravity 2.34.0、Clash Verge Rev（mihomo, TUN 模式）

---

## 0. 一句话结论

Antigravity 弹出的 `Agent execution terminated due to error.` 不是账号被封，也不是服务器抽风，
而是 **Google 按出口 IP 判定为 CN 后返回的地域拒绝**；而本地 `language_server` 的长连接在建立时
就把代理链路钉死了，所以你「明明换了节点」它还在用旧链路重试——这才是「反复被封」的真相。

---

## 1. 现象长什么样

聊天界面出现红色横幅：

```
Error  Agent execution terminated due to error.
Error ID: 485358ca-043c-43bc-89da-3da9f277806a-1510
```

展开详情是原始响应：

```
HTTP 400 Bad Request
Server: ESF
X-Cloudaicompanion-Trace-Id: f65b3887cf688aaf
TraceID: 0xf65b3887cf688aaf

{"error":{"code":400,
          "message":"User location is not supported for the API use.",
          "status":"FAILED_PRECONDITION"}}
```

看上去极其像「账号被处理了」：出现时机不可预测、换账号好像也没用、过一阵又好了。

---

## 2. 排查时间线（含走过的弯路）

| 步骤 | 假设 | 做法 | 结果 |
|---|---|---|---|
| 1 | 是客户端 bug | 看 `~/Library/Logs/Antigravity/language_server.log` | 没有 panic / rpc error，日志干净 |
| 2 | 是网络抖动 | 数日志里的超时 | 只有零星 `stream idle timeout`，与报错时刻不吻合 |
| 3 | 是账号级处置 | 翻二进制里的错误枚举 | 账号处置是另一套码（见 §5），本次不是 |
| 4 | 是地域 | 在日志里找地理字样 | 找到 `Detected location: CN` ← **突破口** |
| 5 | 换节点就行 | 切到 `🇺🇸美国02` | **还是报 CN** ← 第一次反转 |
| 6 | 是探测方法错了 | 用各种匿名接口验证节点 | **全部无效** ← 第二条弯路 |
| 7 | 是连接没断 | `pkill language_server` 逼重连 | 成功 ← 第二次反转 |

### 弯路一：以为「换了节点就该好」

第一次切到美国节点后，日志里仍然每分钟一条：

```
403 PERMISSION_DENIED
reason: LOCATION_NOT_ELIGIBLE
"Your location is not eligible for this service at this time. Detected location: CN."
```

来自 `aicode.googleapis.com` 的 FetchConfig / FetchLicenses。

### 弯路二：想找一个「不用开 App 就能验证节点」的办法，全都失败

这一段最值得记住，因为它决定了后面的方法论：

| 探测方式 | 期望 | 实际 | 为什么不行 |
|---|---|---|---|
| `generativelanguage.googleapis.com/v1beta/models?key=无效key` | 按地域报错 | `API_KEY_INVALID` | 密钥校验在地域检查**之前** |
| `cloudcode-pa.googleapis.com/v1internal:loadCodeAssist` + 伪 token | 按地域报错 | `401 UNAUTHENTICATED` | 鉴权在地域检查**之前** |
| 抓 `gemini.google.com` 页面特征词 | 出现「不可用」 | 抓不到 | 网页端与 API 端的判定通道不同 |
| 读 Antigravity 的 AX 树点「重试」 | 自动重试 | 树是空的 | Electron 没开 `AXManualAccessibility` |

结论：**地域判定只发生在「已鉴权的请求」上**，所以任何匿名探测都不可能复现。
唯一可信的 oracle 是 App 自己发请求后写进日志的东西。

---

## 3. 逆向：这个错误到底是谁产生的

### 3.1 App 结构

```
/Applications/Antigravity.app/Contents/Resources/
├── app.asar                    6.7 MB   Electron 外壳（窗口 / webview / 拉起后端）
├── app.asar.unpacked/
└── bin/language_server         188 MB   Go 写的后端（模型请求 / 认证 / agent 循环 / 日志）
```

后端由 `dist/languageServer.js` 拉起，参数定义在 `dist/lsDefaults.js`：

```js
LS_API_SERVER_URL      = 'https://generativelanguage.googleapis.com'
LS_CLOUD_CODE_ENDPOINT = 'https://daily-cloudcode-pa.googleapis.com'
// 固定 flags
--standalone --override_ide_name antigravity --subclient_type hub
--override_ide_version <ver> --override_user_agent_name antigravity
--https_server_port <p> --csrf_token <t> --app_data_dir antigravity
--api_server_url … --cloud_code_endpoint … --enable_sidecars --host_bridge_url …
```

### 3.2 关键反证（在 188 MB 二进制里逐条搜）

| 字符串 | 在二进制里？ | 说明 |
|---|---|---|
| `Detected location` | ❌ 不存在 | 只可能来自服务端响应体 |
| `LOCATION_NOT_ELIGIBLE` | ❌ 不存在 | 同上 |
| `location is not supported` | ❌ 不存在 | 同上 |
| `Agent execution terminated due to error.` | ✅ 存在 | 横幅是后端**本地**把任意错误统一翻译出来的 |

也就是说：

```
Google 返回 400 FAILED_PRECONDITION
        ↓
Go 后端把错误往上抛，统一包装成 "Agent execution terminated due to error."
        ↓
Electron 渲染成红色横幅 + Error ID（= trajectory_id + 步号）
```

**「看到 agent error」不等于「只有一个错误类型」**——这是判断失误的最大来源。

### 3.3 反面：账号处置长什么样

二进制里存在整套账号/权益状态枚举：

```
QUOTA_EXHAUSTED  SPEND_CAP_REACHED  LICENSE_REQUIRED
ADMIN_SUSPENDED  PARENT_SUSPENDED   DEFERRED  CREDENTIALS_EXPIRED
```

真被停权，报的是这一组里的码，而不是 `FAILED_PRECONDITION + location`。
**这次遇到的是地域分支，不是账号分支。**

---

## 4. 根因：三层叠加

### 第一层：出口 IP 的「归属地」不等于「看起来在美国」

实测对比：

| 节点 | 出口 IP | ip-api / ipinfo 判断 | **Google 判断** |
|---|---|---|---|
| `🇺🇸美国00\|x2倍率 - 电信直连` | `179.255.150.232`（AS906 DMIT） | US ✅ | **CN ❌** |
| `🇺🇸美国02` | `216.195.210.205`（AS138997 Eons） | US ✅ | US ✅ |

中转/落地型节点的落地 IP 被 Google 的 GeoIP 库归到了中国。
**所以「ip-api 说这是美国 IP」完全不能作为通过依据。**
这是第一个反转：不是「没挂 VPN」，而是「挂了 VPN 但落地被判定成 CN」。

### 第二层：长连接把链路钉死了

HTTP/2 连接在**建立的那一刻**就把 Clash 的 chain 固定下来：

```
chains: ['🇺🇸美国00|x2倍率 - 电信直连', '节点选择']
```

之后无论你在 Clash 里怎么切节点，**这条已经建立的长连接仍然走旧链路**。
后端会不断用它重试，于是「换了节点还是 CN」。

佐证：官方代码里处理同类问题的方式就是「切代理 + 强制断开」——

```js
// dist/remote/transport.js
async function routeSessionThroughSsh(ses, socksPort) {
    await ses.setProxy(sshProxyConfig(socksPort));
    await ses.closeAllConnections();     // ← 关键：必须断连接
}
```

### 第三层：空闲时不发请求，导致「假修复」

后端空闲时**完全不产生日志**（实测可以静止十几分钟）。
所以「重启后 `grep -c "Detected location: CN"` = 0」是**假象**——那不是修好了，
只是还没有发过请求。必须去 App 里点一次「重试」，让日志时间戳往前走，才能判定。

## 5. 解决方案

### 5.1 三步操作

```bash
# 1) 切节点（Clash Verge Rev 的 mihomo 控制 socket，不需要 secret）
#    PUT /proxies/<url编码的组名>  {"name": "<节点全名>"}
python3 switch_node.py "🇺🇸美国02"

# 2) 掐掉后端，逼它用新链路重建连接（Electron 会在 ~20 秒内自动拉起）
pkill -f "Antigravity.app/Contents/Resources/bin/language_server"

# 3) 去 App 里点一次「重试」，然后验证
L=~/Library/Logs/Antigravity/language_server.log
grep -c "Detected location: CN" "$L"      # 必须是 0
grep -oE "I[0-9]{4} [0-9:]{8}" "$L" | tail -1   # 时间戳必须往前走
```

判定标准必须是 **「日志时间戳在前进」+「0 条 CN」同时成立**，缺一不可。

### 5.2 选节点的经验规则

- ❌ 避开：香港、中国台湾、任何带「电信直连 / 中转 / relay」的落地
- ✅ 优先：原生 美国 / 日本 / 新加坡 / 加拿大 落地
- ⚠️ `ip-api`、`ipinfo` 判 US **不能**作为依据，只有 App 日志能

## 6. 修好之后的验证数据

日志跨度 `02:19:50 → 14:56:51`，共 2689 行：

| 指标 | 数值 |
|---|---|
| `streamGenerateContent` 调用 | 302 次 |
| `loadCodeAssist` | 131 次 |
| `fetchAvailableModels` | 129 次 |
| `"403 Forbidden"` | **0** |
| `"429` / `"401` / `"503` / `"500 Internal` | **0** |
| `RESOURCE_EXHAUSTED` / `quota exceeded` | **0** |
| `Detected location: CN` | **0** |

**12 小时正常使用、302 次模型调用、零 HTTP 错误。**

### 一个必须知道的 grep 陷阱

这个日志每一行都以 `ERROR: logging before google.Init:` 开头（glog 写 stderr 的怪癖）。
所以拿 `403`、`429` 这种裸数字去 grep，**全是假阳性**（时间戳、长度里就有这些数字）。
必须匹配 `"403 Forbidden"` 这类完整串。

## 7. 本地设置里能不能「伪造地域」？

不能。翻过两处本地状态：

- `~/.gemini/config/config.json`：只有 `plugins.swarm`、`sidecars`、
  `userSettings.{globalPermissionGrants, remoteControlHostname, sandboxEnabledAtV2Migration, voiceName}`
  —— **没有任何 location / region / proxy 字段**
- `~/Library/Application Support/Antigravity/app_storage.json`：全是 UI 布局键（窗口尺寸、会话布局 ID）

但后端有一整套可覆盖的启动开关（`language_server --help` 全量可得），这才是真正的本地杠杆：

```
-model_api_client_type=ccpa|gemini   -override_model_name      -inference_api_server_url
-generative_service_addr             -google_cloud_project    -stubby_auth_mode
-override_oauth_client_id/secret     -api_server_url          -cloud_code_endpoint
-web_bundle_path                     -disable_telemetry       -use_mocked_data / -mock_fixture
```

而且它用 Go 的 `ProxyFromEnvironment`（二进制里 `HTTPS_PROXY`、`ALL_PROXY`、`NO_PROXY` 都在），
**意味着可以只给这个后端进程注入代理，不影响系统其它流量**——这是做工具最干净的切入点。

## 8. 方法论提炼（可复用到任何「服务端偶尔拒绝」的问题）

1. **先分清「谁说的话」**：客户端里的报错文案，往往是被统一包装过的，
   真正的判定依据在响应体和服务端日志里。搜二进制确认哪句话是本地生成的、哪句不可能来自本地。
2. **找唯一可信的 oracle**：任何「替代探测」都要先证明它和真实链路同源。
   本例中匿名接口全部绕过地域检查，只有 App 自己的日志可信。
3. **区分「状态」和「连接」**：配置改了不等于生效，长连接、缓存、连接池都会让你以为改了。
4. **区分「没报错」和「没请求」**：日志为空可能是真的没毛病，也可能是根本没动。
   判定要看「时间戳是否前进」。
5. **不要用第三方 GeoIP 替代服务端判断**：两边用的是不同的库、不同的数据库版本。

## 9. 下一步：把它做成可复用的工具

目标：**别人遇到同样的问题，跑一条命令就好；以后再被判定，再跑一遍。**

```
antigravity-geo-guard
├── detect    tail 日志，命中 Detected location: CN / LOCATION_NOT_ELIGIBLE
├── heal      切节点 → kill language_server → 等 25s → 复验 → 记住可用节点
├── probe     预检：切节点 + 重启后端 + 看日志（用同一个 oracle，不靠 ip-api）
└── guard     常驻守护：每 60s 检查，出错自动 heal
```

边界（必须诚实说明）：它治的是「出口被判 CN」，治不了真正的账号处置
（`ADMIN_SUSPENDED` 那类）。但反过来说，**反复用 CN 出口请求本身**才是真正可能招来
账号风险的行为，所以这个工具确实降低了风险，而不只是「让报错消失」。
